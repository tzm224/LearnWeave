# 执行流程：从材料到设计逻辑

本流程用于首次完整分析。节点或段落的后续展开只重读相关来源与相邻依赖，不必重新执行全套流程。默认中文；读者背景、任务重点及材料自身结构优先于模板。

## 1. 全局阅读与 Document Map

按 [读取策略](reading-strategies.md) 确认主材料、版本和可用范围。先浏览全篇的结构、图表及结论，再补齐正文、备注和相关附录；长文可分块，但在综合分析前覆盖全部可访问内容。委派分块时共享来源位置规则，各块交回“主张、机制、证据、限制、待衔接问题”，主代理负责跨块核对。

建立 `document_map.md`：记录原始章节/页区间、各部分在论证中的作用、实际阅读范围和缺口。它保留原文地图，不承担最终教学主线。同步写来源注册表与 `coverage`，保留物理页号或稳定章节/行号。

完成条件：能指出材料试图改变什么、主要贡献在哪里，以及证据位于何处。暂时不清楚的作者意图标为待确认；只读摘要时不能产出“全篇已分析”。

## 2. 问题、动机与评价条件

从原文重建“当前做法 → 具体失效或代价 → 约束 → 目标”。区分：

- **问题**：使用者或研究者要完成什么；不是方法的名字。
- **约束**：如计算、内存、信息可得性或理论假设；不是任意背景事实。
- **目标**：用什么条件判断方案有用；性能目标与实测结果分开。

对已有方案只陈述材料明确讨论或已核查的内容。未报告基线、替代方案或设计原因时保留空缺，不补写成作者的思考过程。得到问题/约束候选节点及其来源，不以节点数验收。

## 3. Core Idea 与 Architecture

先各写一段：**Insight 改变了对问题的什么认识；Idea 提出怎样的解决方向；Design 将它变成什么结构。** 同一句话只有更换术语时，回原文重查。

以一个典型输入、请求或推理目标走过全流程：

1. 从哪里进入，依赖什么前提或状态？
2. 哪些组件接手，分别承担什么职责？
3. 组件间传递什么数据、控制、状态或证明义务？
4. 何时更新状态、产生结果，哪条边界决定失败或适用范围？

用上述过程解释整体结构，再列必要组件。理论材料对应“定义/假设 → 引理 → 关键论证 → 定理”，不虚构系统模块；算法材料对应阶段、数据表示与不变量。只有一个闭式结论时允许简短架构说明。

完成条件：读者能沿一次执行或论证说出组件如何协作，以及这种组织怎样落实核心 Idea；只列模块名不合格。

## 4. Design Reasoning 与抽象

挑选真正影响核心贡献的决策，逐项重建设计链：

`Problem → Constraint → Insight → Design Decision → Mechanism → Outcome / Trade-off`

这是一组核对问题，不要求每篇材料恰好具备七类节点。缺失环节用“原文未解释/未验证”注明；没有证据的机制解释标为 AI 推断，缺口本身不构造成 evidence。

每项决策回答：解决哪个具体问题、为什么采用这一安排、机制在哪一步产生作用、相比什么改变、带来什么成本。反事实问法可帮助理解，例如“去掉这一机制会破坏什么”；若原文没有消融或证明，只能给出有边界的推断，不能宣称结果已被验证。

替代方案分别标明“作者讨论”或“分析者提出”；比较保持同一目标、资源与假设。来源仅写出实现时，不推定作者考虑过所有替代方案。聚合性能结果可以支持整体效果，不能自动支持每个组件的因果贡献。

从具体决策抽象 `pattern` 时写：可复用的结构、触发条件、保留的不变量、收益来源、失效条件。用一个简短的迁移方向说明映射关系；它是分析结果，不是新领域已验证的结论。没有足够依据时 `design_patterns.md` 说明尚不能可靠抽象。

## 5. 共用节点与 Knowledge Spine

阅读 [数据契约](data-contract.md)，再固定节点 ID。优先保留解释问题、核心贡献、架构及设计选择所必需的单元；无助于主线的术语不必单独建节点。

为每个节点分别判断：

- `importance`：缺少它是否改变对核心贡献或架构的理解？
- `learning_depth`：目标读者需要认识其作用、能解释其工作，还是能推导/实现？
- `level`：应在宏观入口、关键机制层，还是细节层首次出现？

不要由一个字段机械推出另两个。例如关键证明可为 `core + detailed + L3`，其结论在独立 L1 节点中概括；结论节点与证明节点有来源和支持关系。

建立有序 `spine`：通常从问题进入 Idea 和架构，再解释关键设计、证据与权衡，最后抽象思想；可以按材料调整。每一步的 `why_next` 写出前一步留下的具体问题。`knowledge_spine.md` 复用 JSON 中相同 ID 与顺序，不复制一套“主线专用节点”。

## 6. 分层 Knowledge Graph

只为有具体理由的联系建边。为每条边单独写关系方向、`rationale`、来源及归属；两个节点都来自原文不代表它们之间的关系也是作者明确主张。

保留 L1/L2/L3 的累计视图。L1 通常约 5–15 个节点，先突出问题、Idea、架构、关键权衡和结果；更多细节留在后续层，不从结构化结果删除。允许孤立节点和空边集。Graph 回答“为什么有关”；Spine 回答“先理解什么”，不要将主线顺序自动生成为因果边。

使用生成脚本从 JSON 导出 Mermaid。脚本只转换和筛选已存在的关系，不负责发现知识或补齐图。针对某个节点查看邻居图时仍保留原 ID 和证据。

## 7. 分层讲解、核验与交付

先完成两个 JSON，再用 [输出模板](../assets/templates/overview.md) 组织五份 Markdown，生成 Mermaid。正文可在撰写过程中反馈修正结构化内容，交付前保证一致。模板中的占位值必须替换，未适用的项目说明原因或移除。

`overview.md` 默认用约一页解释：一句话、问题与动机、核心 Idea、架构、关键选择、有效机制、证据/权衡/边界、迁移思想。链接到主线、架构分析、来源地图和图谱；不默认展开完整推导或实验表。沿任意节点展开时，先给前置、机制或证据，再由用户需要决定是否深入 L3；可用的 Teach Skill 能接手微观教学，但不作为本技能运行依赖。

按 [质量评审](quality-review.md) 完成结构与内容两类检查。完整覆盖与正确分析是不同结论；遇到不可读取部分时可以交付已完成范围，但在入口指出受影响的结论。不能将部分结果称为全篇分析完成。
